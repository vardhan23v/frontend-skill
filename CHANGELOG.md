# Changelog

## 4.0.0 — 2026-10-27

Ship it. The skill now carries a frontend from a local build to a reviewable pull request, a real CI run and a checked deployment — with the user's identity, not a bot's.

### Added
- Step 12 "Prepare for delivery and deploy": GitHub preflight, branch, commit, PR, CI, GitHub Pages and merge/tag/deploy rules; `references/github-delivery.md` with commands, the PR body template, identity checks and the failure table
- `references/security-headers.md`: CSP baseline, report-only rollout, HSTS and the other headers, host configs for Vercel, Netlify, Cloudflare and GitHub Pages, SRI and the verification commands
- `references/observability.md`: error reporting adapter, Web Vitals, a typed event plan, consent categories with default deny, privacy page and network-panel verification
- `references/accessibility.md`: WCAG 2.2 AA additions (2.4.11, 2.5.7, 2.5.8, 3.3.7, 3.3.8, 3.2.6), core checklist, component checks and the manual keyboard/screen-reader walk
- `references/quality-gates.md`: Lighthouse CI budgets, bundle-size gate, Playwright visual regression, axe in CI and the failure policy
- `assets/github/ci.yml`: generated-project CI that detects npm, pnpm, yarn and bun, runs only defined scripts and uploads test artifacts
- `assets/github/pages.yml`: static GitHub Pages deploy with base-path and SPA fallback notes
- `scripts/verify.sh`: runs install, lint, format, types, tests, build and Playwright; reports undefined checks instead of inventing a pass
- Step 10 receives an eighth verification category, **Delivery**, and step 13 a `GIT` and `DELIVERY` block
- Step 7 security headers and observability sections; step 8 budgets; step 9 visual and axe gates; step 11 delivery failure rows
- Definition-of-done items for headers, consent, CI and identity
- README sections for delivery, security headers, observability and quality gates; v4 validation status
- CI validation for the new references, assets, workflow YAML, `verify.sh`, and for bot authors or `Co-Authored-By` trailers in branch commits

### Changed
- Frontmatter: version `4.0.0`, homepage `github.com/vardhan23v/frontend-skill`, description covers eight verification categories and delivery; compatibility mentions Git and the GitHub CLI
- Verification model: seven categories → eight (code, types, build, tests, browser, visual, accessibility, delivery)
- Accessibility standard: WCAG 2.1 AA → WCAG 2.2 AA
- Step 2 requirement table gains security headers, analytics/consent and GitHub delivery; step 3 gains CI, error tracking and analytics rows
- Step 5 documents the delivery files; step 1 reads the Git remote, workflows, `gh auth` and commit identity
- Step 12 is now delivery and host deployment, not deploy prep alone
- README title, badges and clone URL point at `vardhan23v/frontend-skill`
- Release instructions use `v4.0.0`

### Rules
- The commit author and committer are the user; no bot author, no `Co-Authored-By` agent trailer, no "generated by" footer
- No force-push to a shared branch, no direct push to `main`, no merge, tag or deploy unless asked
- No analytics or marketing request before consent; no PII in events
- Never claim a CI run, deployment or header check that was not run

## 3.1.0 — 2026-10-06

Colour themes, and the skill becomes an agent-agnostic, open-source Agent Skill.

### Added
- `references/themes.md`: eleven named themes (Birch, Paper & Ink, Pewter, Forest, Terracotta, Midnight, Harbour, Citrus, Gallery, Dusk, Brass), each with light and dark token sets as ready-to-paste `:root` and `.dark` blocks, a font pairing no other theme uses, a radius scale, per-mode card and popover shadows, usage notes, and contrast figures generated by the checker
- `scripts/check-contrast.js`: dependency-free WCAG contrast checker for a token file; text pairs must reach 4.5:1 and UI pairs 3:1 (including the `input` outline and the ring on muted fills); warns on OKLCH hue collisions between primary, accent and status colours, status text on muted fills, fill-only accents, pure black/white, inverted dark modes and indigo-band primaries
- `scripts/scaffold.sh`: non-interactive scaffolds for Vite + React, Next.js, Astro, Vue, Svelte and plain HTML
- `scripts/install.sh`: symlinks (or copies) the skill into `~/.agents/skills`, `~/.claude/skills`, a project, or any directory, so `git pull` updates every install
- `LICENSE`: MIT; frontmatter declares `license`, `compatibility` and `metadata.version`
- Step 6 "Colour theme": existing tokens win; a supplied brand derives a theme; otherwise a project → theme table decides, and the choice is named in the plan and the report
- `references/themes.md` wiring: Tailwind v4 `@theme inline` mapping with base rules in `@layer base`, outline-based focus that survives `shadow-*` and forced-colors mode, `color-mix` recipes for hover, selection and secondary-on-primary, and a dark-mode setup without a flash (blocking inline script in `<head>`, `is:inline` for Astro, `color-scheme` on the class, `suppressHydrationWarning` or `next-themes` with `attribute="class"` for Next.js); flat themes use `0 0 #0000` so `shadow-card` never cancels a ring
- `SKILL.md` appendix: the theme tokens in compact form and an inline contrast check, so a single-file install still works
- Verification report: `Theme:` line in PROJECT; definition of done: theme named and contrast checked in every shipped mode
- README: Colour themes section, multi-agent install table, licence
- GitHub Actions: CI (spec frontmatter, theme contrast, appendix sync, links, shellcheck, script behaviour), Release on `v*` tags (zip + notes from this file), monthly Scaffold drift run; Dependabot for action versions

### Changed
- Token set: `surface`, `input`, `accent`, `ring`, `warning` and the `-foreground` pairs added
- Step 2: question batches respect the client's structured-question limits; everything else becomes a stated assumption
- Step 3: points at `scripts/scaffold.sh` first, plain commands second
- Step 6: the visual-design skill reference is optional with an explicit fallback; nothing depends on a skill that may not be installed
- Accessibility verification checks contrast twice: tokens with the script, rendered pages with axe
- Wording is agent-neutral throughout; frontmatter description no longer names another skill
- The skill is a folder (`SKILL.md`, `references/`, `scripts/`); install instructions cover Codex, Cursor, Copilot, Gemini CLI, OpenCode and Claude Code

## 3.0.0 — 2026-10-04

Production-hardening pass. Structure and terminology of 2.0.0 preserved; sections renumbered to fit the additions.

### Added
- Step 0: project classification (new / existing / partially implemented / needs refactoring) with handling rules for each, in front of the existing task-sizing table
- Step 1: run existing install, typecheck, lint, test and build once before changing anything; record pre-existing failures
- Step 2: requirements table with a "default when not stated" and "ask when" column, covering purpose, flows, data, auth and roles, responsive and browser support, accessibility, SEO, performance, states, references, deploy target, env variables and integrations
- Step 3: explicit six-level stack priority and a decision table covering framework, language, styling, component library, state, routing, data fetching, forms, testing and build tooling
- Step 4: backend boundary — trigger list, six rules, API contract location and content, labelled-mock policy
- Step 6: "avoid the generic AI look" guidance; how to analyse a supplied design reference
- Step 7: explicit responsive checklist (navigation, typography, grids, tables, forms, dialogs, buttons, images, overflow, touch); "ARIA only when native semantics cannot express it"; form retry; URL handling; public vs private environment variable table; secret scan of the diff; structured data in SEO; SEO explicitly skipped for private apps
- Step 8: re-render, duplicate-request and Next.js client-component checks
- Step 9: testing decision table (write for / skip for)
- Step 10: verification split into seven categories (code, types, build, tests, browser, visual, accessibility) with the rule for unavailable tools; the literal `BROWSER VERIFICATION: NOT AVAILABLE` block with manual steps; accessibility interaction verification
- Step 11: failure recovery loop with a retry limit and blocker handling; two new rows in the common-failures table
- Step 12: framework-specific deployment requirements, common deployment risks, safe deploy workflow when deployment is requested
- Step 13: fixed-format verification report
- README: supported project types, verification levels, browser verification behaviour, failure/recovery behaviour, Validation Status
